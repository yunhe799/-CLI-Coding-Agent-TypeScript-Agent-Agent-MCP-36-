# 我踩过的三个坑，每个都改掉了一处设计

> 写这篇文章的动机很实在：简历上写"我实现了 X"证明不了什么，能讲清"**我以为是 X，实测是 Y，所以我改成了 Z**"才证明得了。下面三个坑都是真踩的，而且每一个都不是"写错一行代码"，是**判断错了**。

## 坑 1：`git log -S foo --reverse -n 1` 返回空集

背景：我在写一个「代码库考古」MCP server，其中 `find_introduction` 要回答"这段字符串是什么时候引入的"。直觉做法是让 git 只给我最早那次提交：

```bash
git log -S COMPACT_THRESHOLD --reverse -n 1 --oneline
```

**结果是空的**——退出码 0，一行输出都没有。去掉 `-n 1` 就有结果，去掉 `--reverse` 也有结果，两个一起用就没结果。

原因：`-n`（max-count）作用在**遍历阶段**（从新到旧数够 N 条就停），`--reverse` 只是把**已选出的列表**倒过来输出。两个一起用，等于"先选最新 1 条，再把这个长度为 1 的列表倒序"——而 git 在这个组合下的行为是直接不输出。

正确做法简单得可笑：`git log` 默认就是新 → 旧，**列表里最后一条本来就是最早那次**，根本不需要第二次调用：

```js
const oldest = commits[commits.length - 1];   // 最早的那次
```

**教训**：工具的"直觉用法"要实测，不能靠感觉。我如果只写代码、不写测试，这个 bug 会一直躺在那里——因为单看返回值"空数组"不报错，`find_introduction` 只会安静地少给一行。

## 坑 2：目录在 `import` 那一刻就被定死了

`skills.ts` 和 `memory.ts` 里我都是这么写的：

```ts
const SKILLS_DIR = join(process.cwd(), ".mini-skills");   // ← 模块级常量
```

CLI 从项目根目录启动，所以日常用起来**完全正常**——这个 bug 藏了两周。

它是被**评测沙箱**照出来的：评测要给每条用例一个干净的工作目录，于是 `process.chdir(临时沙箱)` 之后，技能和记忆的路径还指在启动时那个目录上。技能展开静默失效，测试立刻红了。

改法：

```ts
const skillsDir = () => join(process.cwd(), ".mini-skills");   // 调用时再算
```

**教训**：模块级常量看起来"只是缓存一下"，其实是在 import 那一刻对**全局可变状态**（cwd）做了快照。这类 bug 不会在日常路径上出现，只在"环境被换掉"时出现——而**测试环境的隔离度，决定了它能照出多深的问题**。这也解释了为什么第 4 周（自建评测集）比第 3 周（写业务 server）更值钱：不是它更难写，是它能**证伪**。

## 坑 3：压缩阈值数错了东西

上下文压缩的触发条件，最早是"消息超过 20 条就压"——这个数字在假模型下工作得很好：

```
读 11 个文件 → 假模型一轮调一个工具 → 1 + 11 + 11 = 23 条消息 → 触发压缩 ✅
```

可换成真模型，同一件事变成：

```
读 11 个文件 → 真模型把 11 个 read_file 合并进同一轮 → 1 + 1 + 1 = 3 条消息 → 压根不触发 ❌
```

**同样一件事，两种节奏差了 20 条消息。**根因是"条数"这个度量根本不是我们关心的东西：我们真正担心的是**上下文被撑爆**，而撑爆取决于**内容体量**，跟模型怎么攒消息无关。

改法：按字符体量估算（≈ token 的粗估），阈值 40KB 左右：

```ts
const size = messages.reduce((s, m) => s + messageChars(m), 0);
if (messages.length <= KEEP_RECENT + 1 || size <= COMPACT_THRESHOLD_CHARS) return messages;
```

这个坑还带出一条更重要的方法论，我把它写进了评测集：

> **mock 可以断言"机制"，live 只能断言"效果"。**

因为 mock 的模型行为是我自己写的脚本，确定；真模型怎么走是它的自由。我第一版评测把 mock 的机制断言（"必须调用 `run_shell`"、"结果里必须有 `Denied:`"、"必须调 `search_history`"）原样搬到 live，结果 36 条里挂了 20 条——**逐条看完，没有一条是 Agent 的 bug**，全是模型选了另一条同样正确的路（它自己在提示词层就拒了危险命令、用 `find_introduction + commit_info` 走到了同一个答案）。

改成"按模式分级"之后：mock 断机制（验证断言本身没写错，必须 100%），live 断效果（危险的事没发生 / 文件内容对不对 / 答案有没有拿到），通过率 44.4% → **96.6%**。

## 附带一个：PowerShell 5.1 不认 `&&`

我给用户的提交命令里用了 `git init && git add . && git commit ...`——在我这边（PowerShell 7.6.5）跑得好好的，到了用户那边（Windows 自带 PowerShell 5.1）直接**解析错误，一条都不执行**。

**教训**：给用户的命令要在**用户的环境**里验证，不是在自己的环境里验证。而且 `;` 不是 `&&` 的等价物——`;` 不管前一条失败都会继续，可能悄悄提交一个半成品。稳妥写法是**一行一条命令**（bash / PowerShell 5.1 / 7 都能直接粘贴）。

## 三个坑的共同点

它们都不是"某个 API 用错了"，而是**判断错了**：

| 坑 | 我以为是 | 实际是 |
| --- | --- | --- |
| `--reverse -n 1` | 拿最早那次 | 返回空集 |
| 模块级常量 | 缓存一下路径而已 | 对 cwd 做了快照 |
| 压缩阈值 | 数消息条数 = 数上下文压力 | 条数取决于模型怎么攒，与压力无关 |

能证伪它们的只有一样东西：**跑起来看**。所以这个项目里最值钱的一行不是某个功能，而是那句

```
✅ ctx-01  ...  (compacted 11 messages / ~55000 chars into a summary)
```

——它把我"以为"的东西变成了可观测的事实。

## 补记：又踩了两个更隐蔽的

这两条是"接通第二个模型"时撞出来的，都属于**"看起来在工作、其实没生效"**那一类——比报错更难发现。

### 坑 4：`--model` 传了，但请求发给了另一个模型

我写了个评测参数 `--model` 用来做多模型对比。跑起来"没报错"，但拿到的分数怎么都不对。查下去才发现：`agent.ts` 里

```ts
const MODEL = process.env.MINI_MODEL || "claude-sonnet-4-5-20250929";   // ← 模块加载时求值
```

而我的 runner 是这么写的：

```js
import { runCase } from "./lib/harness.mjs";   // ← 静态 import，会被提升到最前面执行
…
if (modelOverride) process.env.MINI_MODEL = modelOverride;   // ← 已经晚了
```

**ESM 的静态 import 会被提升到文件最前**，所以 harness（以及它里面的 Agent）在"我设置环境变量之前"就已经加载完、`MODEL` 已经定死了。参数看着生效了，实际是空操作。

修法：把 harness 改成**动态 import**，等环境变量设好再加载。

```js
if (modelOverride) process.env.MINI_MODEL = modelOverride;
const { runCase } = await import("./lib/harness.mjs");   // ← 这时才加载 Agent
```

**教训**：凡是在模块顶层读环境变量的代码，都等于给那个变量做了一次"启动快照"。**参数/配置类的 bug 特点是不报错**——它只是悄悄用了别的值。所以改这类东西之后，一定要**打印出实际生效的值**确认（我就是靠"报告里模型名不对"抓到的）。

### 坑 5：把"限流"误读成"模型分数"

接第二个模型（Kimi）跑评测，第一轮全量结果：**0% 通过**。

如果就此下结论，我会得出一个完全错误的判断——"这个模型在工具调用上不行"。实际原因写在错误信息里：

```
429 … request reached organization max RPM: 3
```

那个账号每分钟只允许 3 次请求，而评测是连着发的，于是**每一条都被限流打回来了**。

修法有两层：

1. 加**退避重试**（命中 429 就等一会儿再试）；
2. 更重要的：把"重试后仍被限流"的用例算作 **skipped**，而不是 failed——因为**那是我的环境问题，不是被测对象的能力**。

```js
if (isRateLimited(r)) { skipped.push(def.id); continue; }   // 不计入分母
```

**教训**：评测跑出 0% 或异常低分时，先怀疑**环境和断言**，最后才怀疑模型。这次要不是我把 `0%` 点开看了每条失败原因，就会把一个"我的账号限流"写成一个"模型不行"的结论——而且它还会被我写进简历。**低分要先证伪自己。**
